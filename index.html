VAT при сбое VIES

Как покупка проходит при недоступном реестре, кто проверяет номер после оплаты и что уже можно проверить перед выпуском.

СхемаКарта задачДомены и стендПлан проверкиКритерии выпускаИсточники

Зачем нужен эпик

VIES проверяет, действителен ли EU VAT номер. Формат сам по себе доказывает только, что номер выглядит правдоподобно. Сейчас при временном сбое реестра checkout может пройти после проверки формата, а результат VIES потом никто не догоняет. Новый поток сохраняет продажу во время сбоя, даёт покупателю шанс исправить номер и применяет правило продавца, если номер остался неверным.

Настройки и страница уже существуют

Базовая проверка

Сначала формат, затем один синхронный ответ VIES

Проверяются страна, префикс и структура. На неверном формате запрос в VIES не нужен. Покупки без EU VAT продолжают использовать прежние правила. Ветка эпика проверяет совпадение структуры до сетевого запроса, а в случае timeout повторно формат не проверяет.

Исход проверки
База

Формат неверен или VIES ответил invalid

Показать ошибку VAT. Продажа с этим VAT не оформляется. Фоновый случай не стартует.

База

VIES ответил valid

Обычная покупка. Налог рассчитывается по действующим правилам. Проверку этого номера в очередь ставить не нужно.

Новый fallback

VIES временно недоступен

Опция выключена: ошибка доступности, покупка блокируется. Включена: оформление продолжается с VAT exemption в применимом сценарии, запрашивается повторная проверка. В текущей ветке выпуска временный сбой на checkout пропускается без этой фоновой задачи.

Только временный сбой + fallback включён
RabbitMQ / Messenger

RevalidateVatMessage

Код отправляет сообщение после сохранения Customer, до гарантированного окончания покупки. Пока VIES недоступен, повторяет очередь. Нормальный ответ записывает true или false. Постоянная ошибка VIES логируется и завершает этот обработчик без повторной проверки.

VIES дал определённый ответ

Valid

isVatValid=true. Покупка остаётся как есть. Письма с просьбой исправить номер не ставятся.

Invalid: день 0, 3 и 6

isVatValid=false. Отрицательный ответ запускает отсчёт. Покупатель получает три напоминания с /<locale>/update-vat/<hash>. Вариант письма берётся из текущего правила продавца. Hash относится к Customer.

Правило по умолчанию

Keep the sale

Оплата и доступ сохраняются. Номер убирается из Customer и реквизитов счетов продажи, связанных с ним. Требуется сверка уже выпущенного PDF, будущих счетов и суммы налога. Случай закрывается через null.

Refund or cancel

Разовая покупка: вернуть исходный платёж. Платёжный план: проверить возврат и остановку будущих списаний. Обычная подписка: отменить будущие продления, сохранить доступ до конца оплаченного периода, прежние списания оставляются. Закрытие после подтверждения операций.

Шаблоны и отправка

Итог получают покупатель и продавец

Шаблон различает сохранение, возврат и отмену подписки. В текущем Keep the sale код ставит оба письма в очередь до изменения счетов. Порядок и дубли при сбоях нужно проверить отдельно.

Два разных сценария. Это VAT покупателя конкретной продажи. Старый процесс VAT в профиле аккаунта с 15 днями и отдельными письмами остаётся самостоятельным. Эпик #78598 · Старый план QA.
Сроки и правило. Day 0 означает день первого отрицательного ответа VIES, а не дату оплаты. Три напоминания и Day 7 планируются сразу отдельными сообщениями. На напоминаниях правило читается заново, поэтому текст может смениться, если продавец поменяет настройку. В ветке Refund or cancel на Day 7 решение фиксируется перед отдельным обработчиком. HTTP-контракты для QA
  • GET /api/dashboard/customer/settings/payment-page и PUT по тому же пути. Поля validateVatViesBackground (boolean), invalidVatNumberAction (keep_sale / cancel_and_refund). Есть альтернативный URL /api/payment-service-module/secure/label/settings/payment-page. Запись требует владельца workspace.
  • Браузер открывает [/<locale>]/update-vat/<hash>. SSR Page Editor читает GET /inner-api/payment-service-module/open/customer/<hash>/invalid-vat. При false возвращаются firstName, taxNumber, countryCode (ISO, nullable), purchaseLink сейчас пустой. Page Editor ссылку покупки не выводит. Иные статусы или неизвестный hash дают 404. Сбой upstream или нарушение контракта может дать 500.
  • Форма отправляет POST /api/payment-service-module/open/global/customer/<hash>/update-vat на текущий origin, JSON {countryCode, vatNumber}, заголовок X-Violation-Response-Format: Rfc7807. Валидный номер и активный домен продавца дают 200. Main обновляет Customer. Ветка эпика добавляет блокировку, повторное чтение статуса и обновление Contact. При гонке там возможен 409.
  • 422 означает ошибку данных или строгой проверки. По PHP временная недоступность VIES оформляется нарушением поля vatNumber. Standalone E2E подставляет общий error path для одного сценария. Записать фактический propertyPath на реальном API. Отдельно сверить GR в стране и EL в номере.

Как подготовить домены и стенд

Для формы важен конкретный hostname. Можно взять отдельный поддомен существующей зоны. Monolith принимает успешный POST только на активном домене того продавца, которому принадлежит покупатель.

Staging: системный поддомен

page-editor-systeme.systeme.club указан в QA sc-124536. Начать с него, чтобы проверить общую маршрутизацию, форму и API без подготовки внешнего DNS.

Staging: кастомный домен

Использовать активный тестовый домен того же продавца. Этот прогон проверяет реальный DNS, HTTPS, маршрутизацию и кэш на внешнем входе.

Локально: два имени

Использовать системный тестовый поддомен продавца и второе имя в *.systeme.local. Так можно проверить форму, API и правило владельца домена через локальный nginx.

Staging: системный → кастомный

  1. Сверить фактические версии Monolith и Page Editor на staging. Для уже выпущенных частей ориентир release. Для проверки нужен синтетический Customer с isVatValid=false, связанный с владельцем системного поддомена. Штатный checkout в текущем release этот случай не создаёт. Взять подготовленный QA fixture у владельца сценария.
  2. Открыть https://page-editor-systeme.systeme.club/en/update-vat/<hash> по утверждённому тестовому hash. Сначала проверить известный несуществующий hash: ожидается 404 в Page Editor. Затем активный: 200, подставленные VAT и страна. В DevTools сверить ответ страницы, same-origin запрос формы и заголовки.
  3. Для повтора взять готовый активный кастомный QA-домен этого продавца. Если его нет и staging поддерживает подключение новых доменов, владелец тестовой зоны добавляет свободный поддомен в Settings → Custom Domains staging-аккаунта, публикует выданные там CNAME и ждёт активации и рабочего HTTPS. DNS-цель и валидационные записи брать из staging. Доступность подключения новых доменов и наличие готового кастомного QA-домена пока не подтверждены. Порядок подключения поддомена.
  4. На кастомном hostname повторить GET с локалью и без неё и POST с новым тестовым случаем. После 200 заново открыть старый URL в новой вкладке: должен быть 404. Через внешний вход проверить Cache-Control: no-store и отсутствие старой формы после обновления. Для проверки письма целиком сделать нужный домен доменом по умолчанию только у выделенного тестового продавца и сверить hostname в отправленной ссылке.

При ошибке маршрутизации сверить правило ALB 558, target StagingPageEditorPublicPagesNew и логи /ecs/page-editor-public-pages-staging. Историческая проверка в задаче различает 404 Page Editor и 404 Monolith по X-Powered-By: Express. Если заголовок убран на edge, сверить логи по времени запроса. Staging QA · Маршрут ALB.

Локально: подготовить hostname и маршрут

  1. Для выпущенных задач собрать нужные версии из origin/release, для сквозного потока использовать epic-113342. Убедиться, что Monolith и Page Editor работают в общей сети sio_network и Page Editor обращается к локальному Monolith. Standalone Page Editor с подменой Monolith годится для проверки интерфейса.
  2. Взять системное имя локального продавца. Например, systemeio-test.systeme.local уже резолвится в loopback на этой машине. Сверить владельца и активность в локальном приложении. Добавить второе имя, например 127.0.0.1 vat-qa.systeme.local, в /etc/hosts. Использовать доверенный сертификат dev-стека, действительный для выбранных имён.
  3. Подготовить локальным fixture активный UserDomain для второго имени у этого же продавца и минимум два Customer с isVatValid=false. Для проверки чужого домена нужен ещё один hostname другого локального продавца. Публичный DNS и AWS для локального варианта не нужны.
  4. В проверенном локальном nginx нет правила /update-vat. В репозитории /home/badr/dev/dev-infrastructure добавить файл docker/nginx/custom-locations/default_server/vat-qa.conf. Этот каталог уже монтируется в контейнер и подключается через include. Пример маршрута для выделенного локального стенда:
location ~ "^(/[a-z]{2,3})?/update-vat/[A-Za-z0-9_]+$" {
    set $upstream http://page-editor;
    proxy_pass $upstream;
    proxy_set_header Host $host;
}
  1. Из корня dev-infrastructure выполнить docker compose exec systemeio-nginx nginx -t. После успеха выполнить docker compose exec systemeio-nginx nginx -s reload. POST /api/payment-service-module/open/global/customer/…/update-vat должен сохранить исходный hostname и идти в Monolith. В этом checkout для префикса уже есть локальный zz-payment-service-module.conf. В другой копии сверить его наличие: более общий /api/payment-service может отправить POST в отдельный Payment Service.
  2. Через браузер открыть https://vat-qa.systeme.local/en/update-vat/<hash>. Проверить GET, POST, сохранённый VAT и закрытие ссылки. С другого hostname проверить, что валидный POST не меняет запись чужого продавца. Полную границу GET отдельно проверить по A05.

Маршрут и fixture выше описаны для подготовки, этот прогон ещё не выполнен. Локальный nginx проверяет поведение приложения. Кэширование CloudFront, TLS и правила AWS проверяются на staging.

Куда смотреть при первом сбое
  • 404 уже на открытии. Сначала выяснить, кто ответил. Если Page Editor вызывал inner GET и получил 404, проверить hash и isVatValid=false. Если запрос не дошёл до Page Editor, проверить nginx или ALB.
  • Форма открылась, POST дал 404. Проверить same-origin, активный домен и владельца Customer, затем убедиться, что запрос ушёл в Monolith. Если ответ 422, смотреть тело и путь ошибки VAT. Если 502, сверить upstream nginx и доступность сервиса.
  • POST дал 200, а старая форма появляется снова. Сверить isVatValid=true и новый inner GET. Если inner GET закрыт, проверить публичные заголовки, кэш и повторное открытие через внешний домен.

Подготовка и доказательства
  1. Записать SHA или digest Monolith, Dashboard, Page Editor, образов worker и версии IaC. Проверить, что контейнеры используют тестовые БД и очереди, почта перехватывается, провайдеры в тестовом режиме. Зафиксировать контекст GrowthBook для конкретного тестового продавца и проверить обе стороны флага.
  2. Создать двух продавцов с отдельными доменами, workspace owner и пользователя без права записи. Завести продавцу системный и активный кастомный домены. В первом потоке подготовить локальные Customer с false, true и null. Использовать отдельный Customer для каждого успешного исправления. Сохранить исходные VAT, страну, тип покупки и снимок счёта. Для реального VIES подобрать утверждённые QA номера и проверить их свежий ответ, статусы из старого sc-106232 со временем меняются.
  3. Для сквозного потока выбрать покупателя из другой страны ЕС и продавца с включённым налогом. Выбрать товар с ненулевым контрольным VAT при отсутствии VAT номера. Подготовить разовую покупку, подписку и платёжный план. Ответы VIES задавать тестовым double на границе HTTP: нормальные valid/invalid, timeout, ошибки доступности, постоянная ошибка и ошибка ответа. Проверить логирование и что код реально вызвал ожидаемый upstream.
  4. На тест сохранить версию, окружение, время, роль, ожидаемое и наблюдаемое поведение, HTTP status/поля, ID заказа/Customer и trace ID, до/после по БД/счёту/ledger, письма и изменение доступа. В общие заметки помещать только обезличенные идентификаторы: полный hash из письма работает как ссылка доступа.
  5. Размечать каждый кейс PASS / FAIL / BLOCKED / NOT RUN. Отложенные сообщения тестировать двумя способами: один раз доказать реальные DelayStamp с границами 0 / 3 / 6 / 7 суток, затем ускорять исполнение на изолированных записях. Команда отправки письма отдельно проверяет шаблон и доставку.
